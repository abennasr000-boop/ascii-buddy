# Decisions

One line per decision where the spec was silent or ambiguous, newest last.

## Phase 0

- Stack: TypeScript + Vite + `vite-plugin-singlefile`, Preact + `@preact/signals`, `idb` for IndexedDB — the stack §3.4 suggests.
- TypeScript 7.0.2 (current stable at build time) rather than 5.x — verified on npm, no blocking API changes hit in Phase 0.
- Departure Mono sourced from github.com/rektdeckard/departure-mono (OFL-1.1, confirmed via the repo's LICENSE file); only the Regular woff2 is embedded. JetBrains Mono ("Smooth" font option) is deferred until Phase 6 actually builds the ASCII font switch, so no unused asset ships early.
- App icon is a hand-generated 1-bit pixel-art heart, produced by a small procedural PNG encoder (`scripts/generate-icons.mjs`, hand-rolled PNG chunks + Node's `zlib`) rather than sourcing external art — keeps the app fully self-authored and dependency-free at 32/180/192/512px.
- Icon `<link>` tags and the web app manifest are injected at runtime (`src/bootstrap.ts`) as base64 data URIs from imported PNGs, rather than static `<link>` tags in `index.html` — keeps them inside the single `dist/index.html` (no separate icon files needed at hosting time) while still supporting "Add to Home Screen".
- All six IndexedDB object stores from §14.1 (`projects`, `cels`, `images`, `thumbnails`, `palettes`, `settings`) are declared at DB version 1 now, even though Phase 0 only reads/writes `projects` and `settings` — avoids a version-bump migration later.
- When IndexedDB can't be opened at all (e.g. a page opened via `file://`, which some browsers deny outright), the app shows a banner and keeps running without persistence rather than hanging on "Loading…" — this is the "degrade gracefully" case §3.2 calls out.
- Home screen omits "Export project file" / "Import project file" (§13.1) — that's `.buddy` format, which is Phase 8 scope. No disabled stub button was added for them.
- Editor's File menu shows "Project settings…" but disabled — its tabs (Canvas/ASCII/Onion) depend on features not built until later phases, so the dialog itself isn't implemented yet rather than shipping a partial one.
- New project's active palette seeds only the "Ink" starter palette (black/white/grays). The other 3 starter palettes and the palette library (save/load/import/export) are Phase 5 scope (§7.3).
- New Project dialog's background swatch uses the native `<input type="color">` rather than building the full 1-bit Colors window/picker (§7.2) — that arrives in Phase 1.
- "Terminal 80×24" canvas preset uses the spec's literal 2048×1228 size rather than the general aspect-rounding formula (which yields 1230 for a plain 5:3 ratio) — the spec calls this preset out specifically to land on exactly 24 rows at 80 columns.
- IDs are short random 12-char base36 strings (`crypto.getRandomValues`), matching the `ID` type's "short random id" comment in §17 — not UUIDs.
- Route state (Home ⇄ Editor) lives only in an in-memory signal, not persisted — reloading always returns to Home. No deep-linking is required in v1.
- The Editor's quick-toggle row (Raster/ASCII, references, onion, undo/redo, focus mode) renders as chrome but stays disabled until each underlying feature lands in its phase.
- Menu-bar quick-toggle controls are sized to the 32px bar height instead of the general 44×44pt minimum hit area — §12.1 allows a control to "look smaller" than its hit area; a real oversized hit-area treatment is deferred until these controls do something.

## Phase 1

- Current drawing color, paper-editing target, pen/eraser sizes and tip shapes are ephemeral editor state (signals), not persisted — the §17 data model has no field for them (only `background`, which *is* persisted), so they reset to defaults each session rather than inventing new schema.
- The Colors window edits one of two targets — "Ink" (current drawing color) or "Paper" (project background) — picked via a small swatch toggle at the top of the window. The spec describes the window's contents (swatch, palette, picker) but not how one picker edits two different color slots; this is the simplest mapping.
- Floating window positions (currently just the Colors window) persist in `localStorage`, keyed by window id + orientation (portrait/landscape) — this is a per-viewer UI convenience, not project data, so it doesn't belong in IndexedDB/project JSON.
- A cel's `version` (§17: "increments on every edit, cache key") increments once per completed stroke or per undo/redo/clear, not per pointermove — a stroke is one edit for this purpose; the display already repaints incrementally per pointermove independent of the version counter.
- Two-finger gestures use only the first two touch pointers for pan/pinch math; a third+ finger is tracked solely for tap-gesture peak-count purposes (three-finger tap → redo) and doesn't otherwise change the pan/zoom in progress. Real multi-touch trackpad-style gestures beyond two fingers aren't specified.
- `setPointerCapture` calls are wrapped in a try/catch helper (`safeSetPointerCapture`) — it can throw in edge cases (pointer already released), and losing capture only means a drag won't keep tracking outside the source element, not a functional failure worth crashing over.
- Canvas rotation gesture (App Settings toggle) stays inert in Phase 1 — it's off by default per §13.4, and actual rotation handling is significant added complexity for an opt-in feature; implementing it is deferred to when canvas transform work is revisited.
- Pencil hover preview is skipped (explicitly marked "nice-to-have" in §6.2).
- No pressure sensitivity, no stroke stabilizer — both explicitly out of scope per §6.2.

## Phase 2

- Default density (γ) tuned from the spec's suggested starting point of 0.5 down to **0.3**, per §5.3's explicit instruction to tune it against the §5.10 targets. At γ=0.5, a default-size (4px) stroke passing through an 80-column grid cell (2048×1536 canvas) only reaches ~0.16 coverage, which maps to ramp index 4/9 — below the "at least mid-ramp" target. γ=0.3 brings that to index 5–6/9 while still keeping true near-zero coverage (a stray sub-pixel touch) at the lightest ramp character. Measured empirically via a real `strokeSegment` call at default settings, not guessed — see `src/engine/asciiConvert.test.ts`.
- A literal single click with the default 4px round brush (no pressure, so always a full ~12px-area stamp) yields coverage ≈0.0096 in an 80-column grid cell, which at γ=0.3 lands around ramp index 3 — not literally the lightest character. The "tiny accidental dot → lightest character" target (§5.10) is treated as being about the threshold curve's near-zero behavior in general (any faint mark should read as light, and disappear at a small threshold bump), not a guarantee that every possible single tap is the absolute lightest glyph — the two targets ("dot is lightest" vs "normal stroke is mid-ramp+") are in real tension at any single γ, since both are produced by the same fixed-width, no-pressure brush; the values above prioritize legible strokes without making a single tap already close to solid.
- Grid statistics (coverage, dominant color) are cached independent of threshold/density/ramp, since those settings don't affect them — only a cel edit (dirty-region incremental update) or a columns change (full recompute) invalidates the cache. Converting cached stats into an `AsciiFrame` is cheap enough (a single O(columns×rows) pass) to always redo in full rather than tracking its own dirty regions.
- Dominant-color tallying per grid cell uses a reused 256-slot scratch array plus a small "touched indices" list (cleared only for touched slots), rather than a `Map` per cell — avoids per-cell allocation overhead across up to tens of thousands of cells at higher column counts.
- Grid overlay renders as thin solid low-opacity lines rather than literally dotted lines (§9's "thin dotted lines" wording) — a CSS repeating-gradient approximation of dashed lines at arbitrary, non-integer cell sizes was not worth the added complexity for a purely visual guide; the functional purpose (showing cell boundaries) is the same.
- "Drawing in ASCII view" (§11) is implemented by keeping the existing raster canvas mounted underneath the ASCII canvas: it's hidden (opacity 0) whenever a stroke isn't in progress, and shown (opacity 1, ASCII canvas hidden) for the duration of a stroke. This reuses Phase 1's pointer/rasterization code completely unchanged and satisfies "thin raster preview while the pen is down, recomputed to characters when the pen lifts" without a second input-handling path.
- The ASCII window (§12.3) in Phase 2 only exposes Columns, a Ramp/Hybrid/Shape style selector (Hybrid/Shape shown disabled — Phase 6), Ramp preset + custom field, and Threshold/Density. "Apply to: Project | Track | Cel" (settings cascade), Character set, ASCII font, Crisp glyphs, and "Characters by color" are explicitly Phase 6 scope per §19's build-phase list, not Phase 2's — omitted rather than stubbed.
- The "Blocks" ramp preset (░▒▓█) is not offered yet, since it needs the extended character set, which is Phase 6 scope. Only Classic/Long/Minimal + custom are available in Phase 2.
- Crisp-glyph rendering (thresholding glyph alpha at 50%, §5.11) is implemented as the engine's fixed default behavior (matching `project.crispGlyphs`'s existing default of `true` from Phase 0), even though the Phase 6 settings toggle to turn it off doesn't exist yet — this is "respect an existing data field," not new scope.
- The ASCII canvas uses `image-rendering: pixelated` (like the raster canvas), not smooth scaling — found during testing that at zoom levels beyond the atlas's cached resolution, smooth CSS upscaling turned already-hard-edged (crisp, thresholded) glyphs into visibly blurry shapes, which contradicts "hard 1-bit edges." Pixelated upscaling keeps the blockiness hard-edged instead, which reads as more consistent with the retro aesthetic than blur, at the cost of visible blockiness at extreme zoom between atlas rebuilds.
- "Reuse the nearest cached size while zooming" (§5.11) is implemented as a single most-recently-built atlas (rebuilt debounced ~120ms after zoom/columns settle), not a multi-size LRU cache of atlases at several resolutions. A multi-size cache would reduce the brief blockiness during an active pinch/zoom gesture, but the single-atlas approach is simpler and the blockiness is transient and self-corrects once the gesture ends.
- Grid statistics (coverage/dominant color) and the derived AsciiFrame are kept in sync with `project.grid.columns` and `project.conversion` by a module-level `effect()` (from `@preact/signals`) in `state/asciiState.ts`, not by a component effect — the ASCII view (and its canvas) is only mounted when actually being viewed, but columns/threshold/density/ramp can change while looking at Raster view (e.g. from the ASCII window), and the engine state needs to stay correct regardless of what's currently on screen.

## Phase 3

- Reference-track transform (move/scale/rotate) uses discrete corner and rotation drag handles rather than gesture-based scale/rotate — two-finger gestures are already claimed by viewport pan/zoom (§6.4), so a second two-finger meaning for the same gesture on a reference track would conflict. Handles are shown only when the reference track is current and the Select tool is active.
- No "free scaling" toggle is offered — `ReferenceCel.transform` (§17) only has a single uniform `scale`, not independent x/y scale factors, so non-uniform scaling isn't representable in the current schema. Corner handles always scale uniformly from center.
- The Layers panel (§8's track headers) is built as its own floating window (`LayersPanel.tsx`) rather than folded into the timeline strip, since Phase 4 hasn't built the real timeline yet — the placeholder timeline bar at the bottom of the Editor stays a placeholder. Track headers will likely move into the timeline's left column in Phase 4; the floating window is a reasonable interim home.
- "Select" doubles as the reference-transform tool (§6.3): it's automatically enabled only when the current track is a reference track, and Editor.tsx auto-switches `currentTool` to `select`/`pen` when the current track's kind changes, so a user never gets stuck with Pen selected-but-disabled on a reference track.
- "Paste image as reference" is wired two ways: the standard `paste` DOM event (works for a real ⌘V or iPad's paste gesture) and, redundantly, an Edit-menu item that calls `navigator.clipboard.read()` directly (since a menu click carries no clipboard data of its own). Both funnel into the same `importImageAsReference`.
- Conversion override per track (Layer menu's "Conversion override…") stays disabled chrome — per §19 this is Phase 6 scope (settings cascade UI), and `ConversionSettings` overrides are already supported end-to-end in the occupancy engine (`resolveOccupancy`) since Phase 2/3's engine work, so wiring the UI later is a pure additive change.
- Fixed in passing (found while testing the Layers panel, not scoped to Phase 3 but blocking manual verification): a `FloatingWindow`'s close button didn't respond to a real pointer click/tap — the titlebar's own `pointerdown` drag-start handler captured the pointer before the button's click could fire, since pointer capture reroutes the matching `pointerup`'s hit-test target. Fixed by stopping propagation on the close button's `pointerdown` in `Window.tsx`. This affected every floating window (AsciiWindow, ColorsWindow), not just the new LayersPanel.
- Also fixed in passing: the *current* drawing track's own `<canvas>` element (owned directly by `DrawingCanvas`, not a component with its own mount effect) went blank if it unmounted (track hidden) and later remounted (shown again), since nothing re-triggered a redraw on remount. Fixed with a callback ref that redraws on every attach.

## Post-Phase-3 (real iPad testing)

- The menu bar was unusable on a real iPad: `viewport-fit=cover` + `apple-mobile-web-app-status-bar-style: black-translucent` (both needed for the edge-to-edge home-screen-app look, §3.2/§13) mean the app draws under the status bar, so the top of the menu bar sat directly beneath the WiFi/battery icons with no room to tap it. Fixed by padding `#root` with `env(safe-area-inset-*)` on all four sides — a no-op in a plain Safari tab (inset is 0 there), but pushes all chrome clear of the status bar/home-indicator/rounded-corner areas in the home-screen app.
- The menu bar's 32px height and the quick-toggle icons' resulting sub-44px hit areas (Phase 0 decision: "deferred to when these controls do something, in later phases") are now the *other* half of the same tap-precision complaint, since by Phase 3 these controls do a great deal. Bumped the bar to 44px and the quick-toggle icon buttons to fill it (44×44) rather than the old 32×32 compression.
- Reference-image import was hard to discover and, worse, silently did nothing: the only working-looking entry point was Edit → "Paste image as reference", which calls `navigator.clipboard.read()` — support for reading *images* this way on iPadOS Safari is inconsistent (and the API requires a secure/HTTPS context at all), so it failed with no feedback. Fixed two ways: (1) a real file-picker entry point (`<input type="file" accept="image/*">`, triggered from a button — the standard, universally-reliable pattern on iOS) is now the primary path, reachable from File → "Import image…", a menu-bar toolbar icon, and the Layers panel's toolbar — this is actually §10.1's *first*-listed entry point, so promoting it to primary over clipboard-paste matches the spec's own ordering, not just a workaround; (2) the clipboard-paste path now shows an `Alert` on failure instead of failing silently, pointing at the working import button. File → "Import image…" is deliberately labeled singular (not "images…", and the file input has no `multiple`) — true multi-select with the options dialog (order/size/start-at/into) is Phase 7 scope (§10.2); this is Phase 3's "single image import" per §19's phase summary, kept honest about its own scope rather than promising bulk import early.
- The Layers panel's reference-track button was renamed/changed from "New reference track" (an empty track, requiring a second unclear step to put an image on it) to "Import image as reference…" as the primary action, since the common case is "add a reference image," not "add an empty container for one." An empty reference track (for a pure paste/drop workflow) is still reachable via a smaller secondary toolbar button and via Layer → "New reference track" in the menu bar.

## Post-Phase-3, round 2 (real iPad testing continued)

- **Root cause of "canvas is stuck, can't zoom" with a reference track selected**: `DrawingCanvas`'s entire pointer/gesture-handling effect (pan, pinch-zoom, everything) was gated behind `if (!container || !canvas) return`, where `canvas` is the *drawing* canvas element — but that element is only ever rendered while the current track is a drawing track (the render only wires `canvasRef` to a track matching `track.id === trackId` inside the "not a reference track" branch). Selecting a reference track — necessary to transform it — meant `canvasRef.current` was `null`, so the guard bailed out and no listeners attached at all: no pan, no pinch-zoom, no anything, for as long as a reference track stayed current. Fixed by gating only on `container` and having the two drawing-only call sites (`blit`, the pointer-capture call in `beginStroke`) re-read `canvasRef.current` fresh at the point of use — both are already unreachable except on a drawing track, so a possibly-null canvas there is safe.
- **Reference transform handles were rendered far too small to hit reliably**: the corner/rotate handles counter-scaled only against the reference image's own `transform.scale`, not the outer viewport zoom applied by `DrawingCanvas`'s pan/zoom. At a typical fit-to-screen zoom (well under 1) combined with a small photo scaled way up to fill a large canvas, the net on-screen handle size could shrink to a few px — small enough that a tap would land on the image itself (triggering a move) rather than the handle (scale/rotate). Fixed by counter-scaling against `scale * viewportZoom` instead of `scale` alone, so handles stay a constant ~32 on-screen px regardless of image scale or canvas zoom; bumped `HANDLE_SIZE` from 28 to 32 for a bit more margin.
- **Reference-transform dragging fought two-finger pan/zoom and could break entirely with two fingers down**: `ReferenceLayer`'s pointerdown handler called `stopPropagation`, so `DrawingCanvas`'s own touch-count tracking (needed to recognize a two-finger gesture) never saw that finger at all; and a second concurrent pointer landing on the image/handles would silently overwrite the single shared `dragRef`, corrupting whichever drag was in progress. Fixed by (1) removing the `stopPropagation` — the container's own drawing logic already no-ops on a reference track, so letting the event bubble is harmless and is required for correct touch counting — and (2) adding a new `touchCount` signal (`state/strokeState.ts`), fed by `DrawingCanvas`'s existing touch-tracking `Map`, that `ReferenceLayer` checks: it refuses to start a new drag while another pointer is already down, and abandons an in-progress drag the instant a second finger arrives, handing full control to the canvas's own pinch/pan gesture.
- The Layers panel's per-track settings (Rename/Duplicate/Delete/static/merge/opacity/Fit-Fill-Reset-Apply) moved from an inline dropdown nested inside the track list's own `overflow: auto` container — which meant reaching the lower items required scrolling the cramped list itself, confusing to operate — into a **separate small floating window** opened via a new gear icon per row, positioned beside the main Layers panel. This directly matches iPad testing feedback ("opens on the side in a smaller window"). The settings panel stays open after non-destructive actions (Fit/Fill/Reset/Apply/rename/duplicate/static toggle) so several can be tried in sequence, and only auto-closes on Delete/Merge down, since those remove the track it's showing.
- **Floating windows (Layers, Colors, ASCII, the new settings panel) could render under the status bar / menu bar**: `FloatingWindow` uses `position: fixed`, which positions relative to the viewport and completely bypasses `#root`'s own `env(safe-area-inset-*)` padding (added earlier this phase). Fixed by adding the same `env()` insets directly to `FloatingWindow`'s inline `left`/`top` — on top of, not instead of, the stored/default offset, so existing drag math (which only ever computes *deltas*) is unaffected.
- Bumped the Layers panel from 260px to 300px wide after adding a fourth per-row icon (the new settings gear) started truncating track names.

## Post-Phase-3, round 3 (real iPad testing continued)

- **A prior fix's own `replace_all` silently missed one of two identical occurrences**: the rotate handle's counter-scale transform was left as `scale(1/scale)` (missing the `* zoom` factor added to the corner handles in round 2), so it stayed the wrong size while the corner handles got bigger and more consistent — caught on this pass and fixed to match.
- **Reference-transform dragging (move/scale/rotate) worked once, then stopped working for the rest of the session** on the real device — every later drag attempt silently did nothing. This points to `dragRef.current` (the single piece of state tracking "is a drag active") getting stuck non-null after the first drag, since `beginDrag` refuses to start a new drag whenever it's already set — a real device apparently hit some path where the matching `pointerup`/`pointercancel` never arrived to clear it, which round 2's `touchCount`-based pre-check could also have caused directly (if `touchCount` itself ever got stuck above 0, no touch-driven drag could ever start again). Since this can't be reproduced or root-caused for certain without a real device to test against, fixed defensively on multiple independent fronts rather than chasing one theory: (1) removed the `touchCount > 0` gate at drag-*start* entirely — it was too easy for it to permanently block every future attempt for what should be a minor two-finger-conflict edge case; the `dragRef.current` truthy check alone still prevents a second concurrent pointer from clobbering an active drag, and the *in-progress* `touchCount > 1` check (which hands off to pinch mid-drag) is untouched, so a wrong `touchCount` there is a much smaller failure mode; (2) added `onLostPointerCapture` next to every existing `onPointerUp`/`onPointerCancel` handler — it's part of the same Pointer Events spec and fires whenever capture ends for *any* reason, so it's a second independent path to the same cleanup; (3) added a 2-second no-movement watchdog timer as a last-resort backstop that force-clears a drag no matter what went wrong upstream. None of these can be fully verified without the real hardware that exhibited the bug, so this needs the next round of iPad testing to confirm.
- **The Layers panel could still render under the menu bar even after round 2's safe-area fix**, because `FloatingWindow` reads a *stored* localStorage position before its own `defaultPosition` — a position saved during any earlier testing session (before today's fixes existed) permanently overrides the new default, forever. Fixed properly this time with a hard CSS floor: `top` is now `max(stored-or-default + inset, inset + menu-bar-height)`, so no saved position, however old or bad, can ever render a window above the bar. The bar's height is now a shared `--menubar-height` CSS custom property so the two stay in sync automatically if it changes again.
- Replaced the gear icon (used for both Home's "App settings" and the Layers panel's new per-track settings) with a new hand-drawn hammer icon — gear read as unclear/generic; a hammer is more concretely "tool/settings" at a glance and was the user's own suggestion.

## Post-Phase-3, round 4 (real iPad testing continued — root cause found)

- **Found and confirmed the actual cause of "reference handles stop working"**: it correlated exactly with the reference image's size relative to the canvas (works at/above canvas size, breaks below it) — a strong, reproducible signal, unlike round 3's guess. Root cause: `TrackCanvas` (the read-only visual for every drawing track *other than* the current one) never set `pointer-events: none`, even though it's purely decorative — a `<canvas>` hit-tests across its *entire* box regardless of which pixels are opaque. Since it's sized exactly to the project canvas (`inset: 0` within the stage) and DOM/paint order (not element size) decides who wins an overlapping hit-test, any drawing track stacked *above* the current reference track in the layer order would silently steal every tap landing within the canvas bounds — while a handle positioned outside those bounds (image bigger than canvas) was never covered by it at all, exactly matching what was reported. Reproduced directly: with a drawing track reordered above a reference track and the image shrunk below canvas size, `document.elementFromPoint` at a handle's center resolved to the `TrackCanvas` element, not the handle, before the fix, and to the handle after. The ASCII-view overlay (`.ab-ascii-canvas-wrap`) had the same latent gap — also purely a rendered view with no reason to intercept anything — so it got `pointer-events: none` too, even though it wasn't confirmed as part of this specific repro.
- Round 3's `touchCount`/`lostpointercapture`/watchdog defenses for a "stuck drag" are left in place (they're correct and harmless regardless), but the size-correlated symptom is now explained by something else entirely, so they likely weren't the real fix — worth remembering if anything *still* feels stuck after this round's fix lands.
- Corner (scale) handles' `borderRadius` dropped from 4 to 0 (sharp corners, matching the app's 1-bit aesthetic — rounded corners read as visually inconsistent) and `HANDLE_SIZE` trimmed from 32 to 24px, per iPad feedback that 32 looked oversized once they were actually usable. The rotate handle stays circular (`50%`) — that shape difference is deliberate, to tell it apart from the scale handles at a glance.
- The Layers panel's floor-clamp (added last round) put the window's top border flush against the menu bar's own bottom border with zero gap — two adjacent 1px lines read as one thick doubled line. Added an 8px gap to the floor.
- Renamed the settings icon again: the hammer didn't read as a hammer at a glance, so — per explicit request — replaced it with a hammer-and-sickle glyph (`hammerAndSickle`), reproducing the shape from a reference image. Noted for the record: this is a real, historically/politically loaded symbol, not a neutral tool icon; flagged that to the user before committing to it as the app's permanent settings affordance. User confirmed keeping it after seeing the first draft, but asked for a closer trace of the reference image — refined once more (thicker/cleaner hook for the sickle blade, a plain rectangular hammer head instead of a wedge that had visually merged into a blob) until it read clearly at both icon size and a 256px blown-up render used to check it.

## Phase 3 sign-off

All Phase 3 spec-listed features (§19: multiple drawing tracks with occupancy, reference tracks with single-image import/paste/drag-drop, opacity/visibility/lock/reorder, static tracks, global reference toggle, reference transform tool, merge down) are built, and every bug found across four rounds of real iPad testing is fixed and re-verified: the menu bar's safe-area/tap-target issues, reference import discoverability, the pan/zoom-killing pointer-effect gate, transform-handle sizing and the `TrackCanvas`/ASCII-overlay pointer-events gap that was silently blocking transform drags, the Layers panel's overlap/scroll/shadow issues, and the settings icon. A full regression pass after all fixes (fresh project → draw → undo/redo → ASCII view → multi-track occupancy → Layers panel → reference import → shrink-and-resize at below-canvas scale with two drawing tracks present → hide-all-references → merge down → reload-and-verify-persistence) turned up no further issues and no console errors. `npx tsc --noEmit`, `npx vitest run` (29/29), and `npm run build` (157.87 KB) are all clean. Phase 4 (timeline/frames/animation) can begin.

## Phase 4

- **Playback deliberately does not drive itself by repeatedly writing `project.ui.currentFrameId`.** That field is the single source of truth every other system (cel loading, ASCII stats, autosave, undo) reacts to, and switching it triggers a real IndexedDB read plus a full grid-stats recompute per track — fine once, but reproducing that every tick at up to 60fps is exactly the stutter §9.2's caching requirement exists to avoid. Instead `playbackFrameIndex` (`state/playback.ts`) is a separate ephemeral signal that only `DrawingCanvas`/`AsciiCanvas` consult while `isPlaying` is true; `currentFrameId` is written once, when playback stops, so every other system keeps working against one settled frame as it always has.
- **Playback caching precomputes both the ASCII frame and a raster bitmap for every frame before playback starts** (`state/playbackCache.ts`), rather than recomputing on the fly per tick — the same reasoning as above (a live recompute per tick is the thing being avoided). ASCII frames are cheap (small typed arrays) and are always fully cached. Building the cache is async and yields periodically (`playbackPreparing` exposes "N of M" for a UI indicator, per §9.2's "without blocking the UI").
- **Found and fixed a real bug in that cache during Phase 4's own testing**: the initial version gave each frame's raster bitmap a fixed per-frame byte budget check and simply left frames blank once ~150 MB was spent — for a 2048×1536 canvas that's only ~12 full-resolution frames, so a 48-frame test animation (the phase's own acceptance criterion) played black/blank for most of its length in Raster view. Fixed per §14.3's own explicit fallback ("render frames on the fly at reduced resolution instead"): the whole cache is now built at ONE shared resolution, computed up front from `budget ÷ frame count`, so every frame gets *some* bitmap — full resolution when it fits, uniformly downscaled (nearest-neighbor, matching the app's pixelated aesthetic) when it wouldn't. `PlaybackCanvas` always draws the cached bitmap scaled to fill the real canvas size.
- ~~**Reference tracks are not re-composited per playback frame.**~~ *Superseded after Phase 7 — see "Post-Phase-7" below (an imported video put a different image on every frame, so frozen references were plainly wrong).* Original note: **Reference tracks are not re-composited per playback frame.** They keep rendering live from `state/referenceStore.ts` exactly as they appeared when playback started, rather than being decoded and drawn into the cached bitmap alongside drawing tracks. This covers the common case (a reference that doesn't vary per frame) without a second image-aware compositor; a reference that's meant to change every frame (e.g. after Phase 7 builds video-derived reference sequences) will look frozen during playback until that's revisited.
- **Onion skin previews are fetched and decoded on demand, not cached across frame moves.** They read whatever animated, visible-per-scope drawing tracks' cels exist for each neighbor frame directly from IndexedDB and re-run the same pure `computeFullGridStats`/`resolveOccupancy` engine calls the live view uses, triggered whenever the current frame or onion settings change (`state/onion.ts`). Given the small `before`/`after` window (0–5 each), redoing this on every navigation is simple and fast enough; a move-to-move cache was not built.
- **Onion color/opacity are applied at render time, not baked into the cached preview data.** `onionLayers` stores only *undyed* ink masks (raster) and each neighbor frame's own `AsciiFrame` (ASCII) — `OnionOverlay.tsx` and `AsciiCanvas.tsx` apply the current `project.onion` color/opacity/falloff when drawing. This means tweaking color or opacity in the onion settings window never needs to re-fetch or re-decode anything.
- **Raster onion tinting composites through a temporary per-layer canvas + `globalAlpha`, not `putImageData` directly** — `putImageData` overwrites destination pixels outright rather than alpha-blending, which would make a farther (fainter) onion layer's opaque write clobber a nearer one instead of blending under it.
- **ASCII-view onion opacity is approximated as a solid blended color** (`engine/color.ts`'s new `blendHex`, blending the onion color toward `project.background` by the effective opacity) rather than true per-pixel alpha, since the glyph atlas (§5.11) only ever caches and draws a glyph fully opaque in a given hex color — there's no per-draw alpha channel to hook into without a much larger rendering change. This is a visible, deliberate simplification: it looks right against a solid-color background and reads clearly as "the ASCII onion skin," but won't blend correctly if the background itself isn't a flat color in some future feature.
- **A track's own settings menu button (`TrackRow` in `ui/LayersPanel.tsx`) uses the "hammer and sickle" icon like everywhere else settings are represented** — no change needed there; new Phase-4-only icons (`onion`, transport glyphs) follow the two established conventions from earlier phases: a custom pixel-art `Icon` for anything conceptual (the onion toggle), and plain Unicode characters for transport-style controls (`|◀ ◀ ▶/■ ▶ ▶|`), matching how Undo/Redo (`↶`/`↷`) were already done rather than adding six more custom pixel icons for arrows every app already renders natively.
- **Frame reordering (drag, and multi-select batch move) only ever touches `project.frames`'s order.** Cels are keyed by `frameId`, not by position in the array (§17), so moving frames around never reads, writes, or re-keys any stored cel data — a `Frame`'s id is permanent from creation to deletion.
- **The expanded timeline's per-cel "has content" dots read a new, separate lightweight existence index** (`state/frameContent.ts`, backed by `db.listCelKeysWithContent`) rather than the existing `liveCels`/`liveReferences` maps, since those intentionally hold only the *current* frame's data (§14.3) — the timeline needs a yes/no answer for every (track, frame) pair across the whole project. The index only checks for a bbox/existence, never decodes pixel data, and is refreshed after autosave and after any structural reload (track/frame add, delete, frame switch) rather than kept live-reactive to every stroke, since a dot lagging by up to one autosave cycle (1.5s default) after an edit is an acceptable trade for not re-scanning the whole project's cels on every pointer move.
- **FPS and playback-mode controls were added directly** (Frame menu items for Loop/Ping-pong/Once and a small `FpsDialog`, plus a tappable "N fps" / mode label in the timeline itself) rather than waiting for the Project Settings dialog, which is still Phase 0's disabled stub — both values already existed in the persisted data model (§17) with no UI to change them at all before this phase, and the timeline's own mockup (§9.4) shows them inline, so this is squarely this phase's own scope rather than scope creep into Project Settings' territory.
- **Multi-select frame batching follows §9.1 literally**: tap the first frame normally-selects-and-navigates; long-press starts a multi-selection (anchored there); a further tap (or Shift-tap, for an external keyboard) extends the range to that frame. Batch Duplicate inserts the copies as one contiguous block immediately after the *last* selected frame, preserving the originals' relative order — batch Move (drag) relocates the whole selected set as a block to the drop target, also preserving relative order.
- ~~Known gap: undo/redo didn't navigate to a command's frame~~ — closed in round 1 below.
- Added `engine/playbackMath.ts` as pure, unit-tested playback-advance math (Loop/Ping-pong/Once stepping, hold-aware elapsed-time advance) separate from `state/playback.ts`'s actual `requestAnimationFrame` loop and signals — the same "pure engine, framework-free, tested" split already used for the ASCII conversion pipeline, and it directly reproduces §9.2's own acceptance example (48 frames at 12fps) as a test case.

## Phase 4, round 1 (real iPad testing)

- **Root cause of "frame content disappears when I add the next frame" (data loss).** Autosave is debounced (1.5s) and `saveCel` writes *whatever cel is live when the timer fires*. Drawing on frame 1 and changing frames before the timer fired meant the reload had already replaced frame 1's live buffer with the new frame's blank one — so the debounced save wrote the blank cel and frame 1's stroke was never persisted (it looked like a stray ⌘Z). Fix: `reloadAllTrackData` (`state/canvasData.ts`) now `flush()`es first, so the outgoing frame is written before its buffer is swapped out. Duplicate/delete/playback-start also flush first, since they read stored cels (a duplicate previously copied a stale version; playback built its cache from stale cels). Leaving the editor now flushes too.
- **Reloads are serialised and latest-wins.** Rapid navigation (A→B→C) could previously let B's slower read land last, leaving frame B's data loaded (and drawable) while C was displayed. Reloads now run one at a time and a reload superseded before it starts is skipped. `DrawingCanvas`'s frame effect also skips its own reload when the data is already loaded for that frame, so it can't overwrite an undo applied in between. It also no longer re-fits the viewport on every frame change (only when a project opens), which had been resetting zoom/pan on navigation.
- **Undo/redo now covers frame operations** (add, duplicate, delete, reorder, hold — single and batch) as `action` commands with closures in `state/history.ts`/`framesActions.ts`, and stroke undo/redo now jumps to the stroke's frame and track first (§6.4). Delete snapshots the frames' cels *and reference-image bytes* so undo restores them; the hold dialog's continuous slider collapses to ONE undo step recorded when the dialog closes.
- **Fixed a latent bug found while doing this:** duplicating a frame shares its reference cels' `imageId` with the source, but deleting a frame deleted that image outright — deleting the copy would have broken the original's reference. Images are now only deleted once no remaining cel references them.
- **Timeline drag rewritten.** The old version reordered `project.frames` live on every pointer-move (re-rendering/re-keying the strip each time: laggy, and DOM re-keying under a captured pointer made frames jump), and any 1-tap drift into a neighbouring chip counted as a reorder — which is what made frames appear to shuffle when tapping. Now: an 8px threshold before a drag starts; an insertion marker while dragging; the reorder is applied once on release; edge auto-scroll near the strip's ends. **Long-press then drag sweeps out a selection range** (interpreting the "drag to select" report); a plain drag reorders (the whole selection, if the dragged frame is in it).
- **Expanded grid:** held frames overlapped their neighbours because the header was widened with an inline `width` while the grid columns stayed a fixed 28px; column widths are now derived from each frame's hold. The selected-frame border didn't show in the grid because the header's own border rule was declared after (and overrode) the shared `--selected` rule; it now has its own bolder style. Grid headers also show "×N".
- **Timeline default now follows orientation on rotation** (`timelineUi.ts` re-applies §9.4's default when the viewport crosses the portrait/landscape line); previously it was computed once at load.
- **ASCII view during playback showed the cached raster on top of the ASCII** because `PlaybackCanvas` ignored the view; it now takes the same opacity rule as the live raster layers (hidden in ASCII, faint if "Show drawing under ASCII" is on).
- **Not a bug:** the ASCII window's Style selector only has "Ramp" enabled — Hybrid and Shape are Phase 6 by design (the buttons are disabled with tooltips). Ramp presets/custom ramp, threshold, density and columns are the settings that work today.

## Phase 5

- **Fill boundaries** come from a per-pixel composite of all *visible drawing tracks* (top-most non-zero index wins), while pixels are written only to the current cel (`state/fill.ts`, pure logic in `engine/fill.ts`). The "Edges" option (All / Track) is in the tool palette. The flood fill is a scanline algorithm that decides the region on the untouched boundary before writing, so boundary and target may safely be the same buffer. A fill whose seed already has the fill color is a no-op (nothing pushed to history).
- **Undo for fill/selection reuses the existing stroke command**, via `commitCelEdit` (`state/celActions.ts`): a before/after dirty-rect crop, pushed only if something actually changed. No new command kind was needed for pixel edits.
- **Eyedropper samples the visible stack, not just cels**: it composes paper + every visible track bottom-to-top on a 1×1 canvas, drawing reference images with their real transform/opacity — so what you pick is what you see. It always adds the picked color to the table. An empty spot picks the paper color (consistent with "the color under the point"). In ASCII view it picks the grid cell's character color, or paper when the cell is empty. Long-press (400 ms, one finger, finger-drawing off) and Option-click work with any tool; the tool itself acts with pen/mouse (and finger only if "Draw with finger" is on), like every other tool.
- **Select works as "lift on first change".** A new selection just records a block (pixels + mask) and leaves the cel alone. The first move/scale/flip/rotate/nudge *lifts* it (cuts the pixels out of the cel into a floating block drawn by `SelectionOverlay`); committing stamps it back — transparent floating pixels never erase what's underneath — and records ONE undo step for the whole gesture sequence. Committing is triggered by: tapping outside, changing tool or track, any `flush()` (which covers frame changes, playback start, duplicate/delete frame, save-now, backgrounding), and any undo/redo. Autosave never fires mid-drag (`commitSelection` refuses while a drag is active).
- **Corner handles keep proportions; edge handles stretch one axis** (animators want squash-and-stretch), always resampled nearest-neighbour from the block as it was when the drag began, so dragging never accumulates blur/drift. Rotation is 90° steps only (spec). Flips/rotation act about the block; rotation keeps the centre.
- **Marching ants are an SVG outline traced from the mask** (`maskOutline`: boundary edges chained into loops, collinear points merged — a rectangle is 4 vertices) with black + white dash paths animated in CSS and `vector-effect: non-scaling-stroke` so the dashes stay constant-size at any zoom. Hit-testing (handles, inside-to-move) is done in canvas space, not on DOM elements, so a selection never fights the canvas's own pointer handling; the action bar stops pointer propagation instead.
- **Internal clipboard** stores pixels + mask + position + a *hex* palette for the used indices, so pasting across projects re-maps colors into the destination's table. ⌘V is disambiguated from "paste a system image as a reference" (§10.1): if the user copied inside the app and the window hasn't lost focus since, ⌘V pastes the selection; otherwise a system image becomes a reference as before. The Edit menu's Paste is always the internal clipboard; "Paste image as reference" stays a separate item.
- **Snap to grid cells** moves the *delta* in whole-cell steps (so the selection stays aligned relative to where it started); default follows the view (on in ASCII), overridable from the action bar.
- **Select tool availability changed**: it's now enabled on unlocked drawing tracks as well as reference tracks; the auto-switch to Pen only happens when coming back from a reference track (where Select meant "transform").
- **Palette library storage**: IndexedDB `palettes` store (declared since Phase 0). Starter palettes are seeded once per browser (a localStorage flag, with fixed ids so a re-seed can't duplicate them). `.hex` parsing tolerates `#`/no-`#`, 3-digit shorthand, trailing comments and duplicates; `.gpl` reads `Name:` and RGB rows. Export uses a Blob + `<a download>` (the share sheet is Phase 8).
- **Palette edits (add/remove/reorder/load) and Replace color are undoable** (`action` commands). Replace color rewrites one table entry, so every pixel using it recolors everywhere at once; a palette swatch showing the old color follows it, and the current ink follows too if it matched.
- **Remove unused colors compacts the table and renumbers every stored cel** (rather than leaving holes and reusing slots), because that is the only way to genuinely free capacity without ever risking a slot being reused while an old undo record still references it. Because of that it **clears undo history** and asks for confirmation first, saying so. Cels are rewritten before the project JSON.
- **Fixed a real bug found while testing undo across frames:** `reloadAllTrackData` returned early when superseded by a newer reload, before the target frame's data was actually loaded — so an undo that jumped frames applied itself to the *previous* frame's buffer and silently did nothing (yet consumed the history step). It now resolves only once the newest reload has finished.
- Not built (not in spec / deferred): free-scale toggle, arbitrary-angle rotation, eyedropper loupe — see IDEAS.md.

## Post-Phase-5: projects getting mixed up (real iPad report)

Symptoms: opening one project sometimes opened another; sometimes a frame from a different project showed inside a project. Not reproducible with a single quick pass in the desktop browser (it is timing-dependent, and iPad storage is slower), so this round fixed every mechanism found by reading the code rather than one line:

- **The Home screen re-read every project from storage each time it appeared** (`loadProjects()` in Home's mount effect) and replaced the in-memory list. Two consequences: (1) if the editor's last save hadn't landed yet, Home read an *older* copy of the project and overwrote the newer in-memory one — and the next autosave then wrote that older copy back over storage (lost frames/colors, a project "reverting"); (2) the grid was re-sorted by `updatedAt` a moment *after* it appeared, so a tap could land on a different card than the one under the finger — very likely the "opens another project" symptom. Now the list loads once at app start (`App.tsx`) and lives in memory; Home sorts it (by `updatedAt`, ties by id) synchronously on render, so it never rearranges after appearing.
- **Leaving the editor now waits for pending saves** (`leaveEditor()` awaits `flush()` before navigating).
- **`flush()` could return before an earlier save had finished** (it returned immediately when nothing new was dirty, even if a previous flush was still writing), so callers that `await flush()` (frame switch, leaving, playback) could read stale data. It now returns a promise for *everything* in flight. It also reads the project at write time instead of before its awaits, so overlapping saves can never let an older snapshot land last.
- **Nothing cleared the editor's module-level state between projects.** ASCII frame + stats, onion previews, the timeline's content dots, the frame multi-selection, live reference images and playback all lived on after leaving, so a newly opened project could briefly render the previous project's ASCII frame (in its own colors) until its own load finished — on a big project on iPad that can be long enough to look like "a frame from another project". `resetEditorSession()` (`state/session.ts`) now wipes all of it when the editor closes, and it also cancels every queued/in-flight reload (`cancelPendingReloads()`), so a slow load that was started for the old project cannot land after the switch. Reference-image loading got the same stale-guard the drawing cels already had.
- **Duplicating a project shared its reference images with the original** (image records are keyed by id alone and deleted per project), so deleting either project deleted the other's images. Duplicates now get their own image records.
- Verified with a stress script (30 rapid open/leave cycles between two projects, leaving at 0/30/80/200 ms and after load, with one project in ASCII view): every project showed its own frame count and pixels every time, and the Home order stayed fixed after editing the older project.

## Phase 6

- **Conversion is now two pure stages**: `convertTrackCells` (per track: which cells it claims and which character each gets — Ramp, Shape, Hybrid, colors-to-characters) and `resolveOccupancy` (walk visible tracks top to bottom; cells claimed above are skipped, so lower tracks never pay for shape matching there). `resolveOccupancy` gained an optional context (templates, extended set, color map) and each track a `celConversion`; effective settings = project ⊕ track ⊕ cel (`effectiveSettings`, §5.7). Existing behaviour and tests are unchanged.
- **Sub-grid bins (§5.2)** are computed in the same single pass as coverage and dominant color (6 × 12 bytes per cell, coverage quantised to 0..255) — but only for tracks whose *effective* style is Shape/Hybrid (`needsBins`), and incrementally for dirty cells after a stroke. Ramp-only projects pay nothing.
- **Shape matching deviates from the spec's "cosine similarity" in two tuned ways, because plain cosine failed the §5.10 line targets on real strokes.** Measured with real 4 px pen strokes against the real Departure Mono glyph masks (the numbers below are share of positions/cells giving the expected glyph):
  - Plain cosine + a linear ink penalty: a centred horizontal line became `+`/`=` (never `-`), a vertical line became `|` only when it sat in the middle of the cell (~38% of positions), diagonals were ~15–20% `/` `\`; slivers of ink at cell edges (the pen's width spilling into the neighbour) matched arbitrary big glyphs.
  - **Translation tolerance**: each glyph is also matched shifted ±2 bins sideways and ±1 bin vertically at 0.02 cost per bin (a pen line lands anywhere in a cell, unlike a glyph stem). Vertical lines → 90–100% `|`, diagonals → ~65% `/` `\`, mid-cell horizontals → `-` (the rest are `_` low in the cell and `'` high — correct).
  - **Log-ratio ink term** (`0.05·|ln((cell ink+ε)/(glyph ink+ε))|` instead of a linear difference), so slivers pick light glyphs.
  - Blurring cell and templates was tried and gave nothing measurable, so it isn't used. Everything else is as specified (cosine on the bin vectors, deterministic tie-break by candidate order).
  - Sparse (CSR) shifted templates keep it fast: the worst case I tried (320 columns, 22k inked cells) is ~70 ms on desktop.
- **Default shape characters were tuned** (§5.5 says the suggested set is "to be tuned with visual tests"): dropped `+ x = o [ ] < > ^ v`, keeping `- _ | / \ ( ) ' , . : ;`. With the heavy glyphs present a centred pen line could never come out as `-` (0% of positions vs ~67% without them). They're one tap away (**+ Heavy**) and the field is fully editable. *Projects created before this change keep their old saved set — tap **Default** in the ASCII window to adopt the new one.* Also: the spec's "0°/45°/90°/135°" targets are interpreted on the **character grid** (one column per row), since cells are 1:2 and a pixel-space 45° stroke is genuinely a shallow `_ - '` chain rather than `/`.
- **The §5.10 line targets are now unit-tested against real glyphs**: `engine/fixtures/departureMonoShapeBins.ts` holds the real glyph masks (captured once from the browser, since Node has no canvas/font) and `shapeTargets.test.ts` draws actual pen strokes through the actual stats pipeline.
- **Glyph templates are rendered from exactly the pixels that get drawn** (`canvas/glyphRender.ts` is shared by the atlas and the templates), for the active font, into a single library covering every shape character any conversion could pick (project + track overrides + cel overrides seen this session + the extended set). Each conversion selects its own subset (`allowedIndices`). Until templates exist, Shape/Hybrid fall back to the ramp rather than showing nothing, then recompute.
- **Worker** (`workers/asciiWorker.ts`, inlined with `?worker&inline`, IIFE format for older iPadOS Safari): runs the same `resolveOccupancy` off the main thread whenever a frame involves shape matching (`state/asciiConvertService.ts`); Ramp stays synchronous so toggling views and sliders is instant. Live view, playback cache and onion skin all go through it. Verified identical output to the main-thread path, and verified in the production single-file build. If a Worker can't be created (or errors) it silently falls back to the main thread. While a conversion is pending the previous frame stays visible and a stale result is dropped (sequence-guarded). **Simplification vs §5.5**: after a stroke the *whole frame* is re-converted in the worker rather than only dirty cells (the statistics are still updated incrementally); the copy + conversion measured ≈20 ms for a 160-column frame, so per-cell incremental shape conversion wasn't worth the added state.
- **Cel overrides live on the cel** (`LiveCel.conversion` → `DrawingCel.conversion`, already in the §17 model) and are persisted with it — an *empty* cel that carries an override is now kept in storage (bbox null) instead of being deleted. A `celOverrideKeys` index (built with the content dots) drives the timeline's ◆ marker; track overrides show ◆ in the timeline row header and Layers panel. "Apply to: Track/Cel" fall back to Project when a reference track is selected.
- **Settings edits are not undoable** (same as the project-level ASCII settings before). Noted in IDEAS.md.
- **Colors-to-characters**: a mapped dominant color wins over the style *after* the threshold has decided the cell is claimed (§5.8). The table takes one code point per color (so block/box characters work). "Remove unused colors" remaps the table's keys along with the cels.
- **Extended character set** adds the `Blocks` ramp preset and appends box-drawing/block characters (`─│┌┐└┘├┤┬┴┼╱╲╳▀▄▌▐`) to every Shape/Hybrid candidate list. **ASCII font → Smooth** is JetBrains Mono (Latin subset, OFL-1.1, license bundled and named in About); glyphs it lacks (box-drawing, blocks) fall back to Departure Mono via the font stack so nothing renders as tofu.
- **Fixed a real bug found while testing**: `AsciiCanvas` only built its glyph atlas once, and bailed if no frame existed yet — so when the first frame arrived later (now common with shape conversion), the ASCII view stayed blank forever. It now builds the atlas whenever the first frame shows up (and again when the font changes).

## Post-Phase-6: "a filled area looks blank when zoomed out"

- **Checked, and the paper is not being rendered blank.** With a large solid area in Shape mode, the frame data holds the characters in every inked cell (627 non-empty cells in the test, mostly `)` `\` `,` `|`), and the on-screen ASCII layer paints a steady 4–7% of its pixels as ink at *every* zoom level from 100% down to 10% (the glyph atlas is built at the on-screen cell size, clamped to at least 6 px, then scaled by the browser). What you see zoomed out is thin 1 px vertical strokes being averaged down by display scaling — a visual effect of the medium, not missing data. Shape is a line-following style; filled areas read better in **Hybrid** (dense ramp characters in the fill, shape characters on the strokes) or Ramp.
- **But the check turned up a real latent bug that would have made exports blank in exactly this situation, fixed now:** "Crisp glyphs" thresholded glyph alpha at a fixed 50%. At small cell sizes thin glyphs never reach 50%: at a 4 × 8 px cell the Pixel font's `|` `'` `.` `:` have a peak alpha of 127, so *the whole glyph was erased* — a filled area of `|` would render as empty paper. The live view never goes below a 6 px cell, so it never showed on screen, but a low-resolution export (small cell size) would have. `engine/glyphMask.ts` (`crispenAlpha`) now thresholds at 50% or at 50% of the glyph's own peak, whichever is lower, so any glyph with ink keeps its strongest pixels at any size. Verified with real rendering: no default shape character (or `# @ % *`) loses all its pixels at any cell size from 2 × 4 up, in both fonts; unit-tested. The function is pure and lives in the engine, so exports (Phase 8) use the same one.
- **Export rule for Phase 8** (recorded so it isn't forgotten): every export renders from the `AsciiFrame` data at the *chosen output size*, never from a screenshot of the zoomed screen, and uses `crispenAlpha` for crisp glyphs — so what is exported is independent of on-screen zoom.

## Phase 7

- **Image import writes in two phases so Cancel and Undo are trivial** (`state/importActions.ts`). Phase A decodes/extracts each item, renders it at its stored size and writes the image to storage, journaling every id — nothing in the project changes, so **Cancel** just deletes the journal (verified: frames, tracks and stored-image count unchanged after cancelling mid-way). Phase B commits quickly and all at once: creates the missing frames and the track, backs up any cels being replaced, writes the new cels, updates the project, and pushes **one** history command. Undo removes all of it (keeping the new images' bytes in memory only so Redo can restore them, and putting replaced cels + images back); Redo re-applies. No orphaned images were left in any of the flows I tested (place, replace, undo, redo, cancel).
- **Sizing bakes the canvas shape in where the reference transform can't express it.** A reference transform is a uniform scale, and the canvas stage does not clip, so *Stretch* (non-uniform) and *Fill (crop)* would otherwise look wrong (distorted-by-nothing / overflowing the paper). Both are rendered at exactly canvas size with the distortion/crop baked in (scale 1). *Fit* and *Original* store the image at its natural size (downscaled to at most the canvas, never upscaled, §10.4) and use the transform's scale (`planImage`, unit-tested). Trade-off (noted in IDEAS.md): a Fill import can't be un-cropped later.
- **Natural sort** is an `Intl.Collator` with `numeric: true`, case-insensitive, with a stable index tie-break; verified with a 12-file shuffled set (frame *k* held image *k*).
- **Entry points**: File → Import images… always opens the dialog (multi-select); the toolbar/Layers photo button keeps the validated quick path for one image and opens the dialog for several; dropping several images opens the dialog, a single dropped image still goes straight onto the reference track (§10.1). Default *Start at* follows §10.2 (Frame 1 for a single empty frame, otherwise after the last); *Into* lists new + existing reference tracks; existing cels in the target range are counted and need a confirmation.
- **Video uses an `HTMLVideoElement` with one `seek` per frame** (not Mediabunny/WebCodecs) — the spec allows either and says to choose what works on iPad and log it. Reasons: it's the only route that already plays iPhone `.mov`/HEVC and `.mp4` in iPadOS Safari with no codec code or extra dependency, and it keeps the bundle small. Each sample sets `currentTime`, waits for `seeked`, then (where supported) `requestVideoFrameCallback` with a 250 ms cap so a missing callback can never hang, then draws to a canvas. Sample times are `start + i/fps`; frame count is `round((end − start) × fps)` (5 s × 12 fps = 60; 4.2 s × 12 = 50). Sources with no declared duration (e.g. browser-recorded WebM) are handled by seeking past the end to resolve it. **Verified end-to-end only in a desktop Chromium (a generated 3 s test video: trim, FPS sampling, set-project-FPS, cancel, correct successive frames); iPad Safari and real HEVC are not testable here — that is the first thing to check on the iPad** (see TESTING.md). If it proves slow or unreliable, IDEAS.md lists the WebCodecs route.
- **A broken video fails the whole import** (rolled back) rather than importing a partial sequence; an unreadable *image* is skipped and reported, the next image taking its frame.
- **Set project FPS to match** clamps to 1–60 and is included in the same undo step. Above 300 frames the dialog warns (§10.3) but doesn't block.

## Post-Phase-7: long animations (real iPad report — 189-frame video import)

- **Playback now animates reference tracks.** The Phase 4 shortcut (references stayed as they were when playback started) was fine for a single reference photo but wrong the moment a video import put a different image on every frame: the counter advanced while the picture stayed stuck. `buildPlaybackCache` now composites every visible track in stack order — drawing tracks *and* references, with each reference's transform and opacity — into each frame's cached raster, and also keeps a references-only bitmap so ASCII view can still show references under the characters without the drawing raster showing through. While playing, the live `ReferenceLayer`s are not drawn (the cache is the source), and `PlaybackCanvas` picks raster vs references by view. The two bitmaps share the one §14.3 budget, so with references present frames are cached at a lower resolution (a 189-frame, 2048×1536 project plays at roughly 0.18×; photographic references are smoothed when shrunk, drawn pixel art stays hard-edged). Hidden references (per track, or "hide all references" incl. the hide-during-playback setting) are left out of the cache.
- **Preparing playback is now visible and ~10× faster.** Pressing Play on a long animation used to look like nothing happened while the cache built (the progress signal existed but nothing displayed it); the timeline now shows "Preparing n/N…". The build also composited every frame into a full-resolution canvas and then shrank it; it now draws straight at the cache size — 189 frames went from ~15 s to ~1.1 s.

Now: **touch/pen — a swipe scrolls (`touch-action: pan-x`), a tap selects the frame, and reordering needs a long-press first** (the frame "lifts", with a haptic tick where supported), then drag; the strip's `touchmove` is only blocked once a frame is lifted so the finger isn't fighting the scroll. **Mouse — dragging still reorders immediately** (a mouse can't scroll by dragging). Long-press still starts a multi-selection (tap another frame to extend the range); the long-press-then-drag *range sweep* added in Phase 4 is gone — that drag now reorders, as requested. Grid cells and track names in the expanded timeline select on release (and only if the finger barely moved) instead of on press, so scrolling the grid no longer selects things under the finger.

- **"|◀ stuck at frame 5":** the first/previous/next/last buttons did work in my desktop reproduction of a 189-frame project (current frame and scroll position both correct), so the report is most likely a consequence of the accidental reordering/scroll problem above. To make it robust regardless, the strip now scrolls with explicit `scrollLeft` maths instead of `scrollIntoView` (which also scrolls ancestors and misbehaves inside iOS scroll containers), and every transport button re-centre the strip on the current frame even when the current frame didn't change — e.g. pressing |◀ while already on frame 1 after scrolling away now brings frame 1 back into view. ## Frame multi-select: one by one, with a Range toggle (post-Phase 7 feedback)

- Selecting frames is **frame by frame** by default. Long-press (or Shift-tap on a mouse) starts a selection; from then on a tap toggles that frame in or out, and nothing else changes.
- The fast "everything between the anchor and this frame" selection is now behind a **Range** toggle in the selection bar (next to Duplicate / Hold… / Delete / Done). While it's on, a tap selects from the anchor (the last frame you selected) to the tapped frame. Shift-tap still does the same on a mouse.
- Range mode switches itself off when the selection is cleared (Done, deselecting the last frame, a reorder, project change).
- Long-pressing a frame that is already in the selection keeps the selection (so a group can be dragged to reorder); long-pressing an unselected frame starts a fresh selection with it.

## Phase 8 — Export

- **Everything renders from stored data at the chosen output size** (`export/frameLoader.ts`, `export/frameRenderer.ts`) — never from the screen. Each frame is decoded from IndexedDB, converted with the same pipeline as playback (occupancy, cascade, Shape/Hybrid through the same worker), and drawn with the same glyph atlas and `crispenAlpha` rule as the live view, so an export is independent of zoom, view and what happens to be loaded. Reference tracks, hidden tracks, onion skin, the grid overlay and selections are never included (§15.1). Exports call `flush()` first so the very latest strokes (and a floating selection) are included. Verified: the exported ASCII PNG has the crisp, complete lines at 2048×1536 (the "zoomed-out fill looks blank" worry can't apply to exports), and a project with a reference photo exports with no colored pixels.
- **Size** is 1×/2×/4×/custom width of the *canvas* (raster) size, with the resulting pixel size shown live. The ASCII grid is drawn cell-by-cell at `round(col × cellW)` with the atlas cell rounded *up*, exactly like the screen, so glyphs stay 1:1 crisp at any output size. Sizes above what iPad Safari can render (**16,777,216 pixels per canvas**) are refused in the dialog with an explanation rather than failing halfway; MP4 rounds up to even dimensions and says so.
- **Two steps: Export, then Share/Download** (`ui/DeliverPanel.tsx`). The Web Share API only opens from a fresh tap, and a long render in between uses the tap up — so the dialog renders first, then shows *Share…* (only when `navigator.canShare({files})` says it works) and *Download* as buttons of their own. That is also why "Copy text" shows a preview and a Copy button. File → **Copy frame as text** tries a one-tap copy and falls back to the dialog if the browser refuses.
- **Runs on the main thread, in small awaited steps** with a progress bar and Cancel, not in a worker (§15.1 says "where possible"). Canvas text rendering and the WebCodecs encoder are the parts that don't move to a worker reliably on iPad Safari; the actual conversion for Shape/Hybrid frames already goes through the existing worker. A 20-frame 2048×1536 raster GIF took ~2 s, the same as MP4 ~1 s, in the desktop check.
- **GIF** (gifenc): frame delays are whole hundredths of a second with *cumulative* rounding (a 12 fps animation still totals exactly its length), never below 2 cs because browsers turn shorter delays into 100 ms; the dialog warns above 50 fps. Each frame uses its exact colors as its own palette when there are ≤256 (always true with crisp glyphs and pixel art), and falls back to gifenc's quantizer for frames with more. **Transparent GIFs** use a reserved transparent index and dispose-to-background on *every* frame (otherwise the previous frame shows through the holes). Loop forever/once.
- **MP4** uses Mediabunny + WebCodecs (`canEncodeVideo('avc')` is checked first; even dimensions; Standard/High presets; holds are real sample durations; "repeat N times" repeats the sequence). If WebCodecs can't do H.264 it falls back to `MediaRecorder` on `canvas.captureStream()` (real time, MP4 or WebM depending on the browser); if neither works the dialog says so and suggests GIF. The video library is code-split into its own module and only loaded for MP4 (the single file grew from ~285 kB to ~585 kB with gifenc + Mediabunny). *Verified: an MP4 made here decodes in a `<video>` with the right size and duration; iPad Safari's encoder is the thing to check.*
- **PDF is written by hand** (`engine/pdfWriter.ts`, ~150 lines, no jsPDF): pages hold zlib-compressed RGB images, and for ASCII content an **invisible Courier text layer** sits over the picture so the art can be selected, searched and copied. The spec prefers real vector text with the embedded font "when feasible"; embedding needs a TTF and the bundled fonts are woff2 only, so the picture is a bitmap at the chosen size and the selectable text is a Courier stand-in aligned to the same grid (non-ASCII characters in the text layer become spaces). One frame per page (A4, Letter or fit-to-artwork; orientation automatic/portrait/landscape) or a **contact sheet** with frame numbers under each frame, laid out to need the fewest pages (frames are rendered only as large as their cell needs, ~200 dpi). Checked by rendering both with macOS's PDF engine — which also caught a real bug (fflate's deflate is raw; PDF needs zlib framing, so the first version showed blank pages).
- **TXT** (UTF-8, extended characters kept): `--- frame N ---` headings with a blank line between frames, or form feeds; optional trailing-space trim; a single frame has no heading. **Golden test** (`textExport.test.ts`) pins the exact text a fixed drawing converts to.
- **HTML player** (`engine/htmlPlayer.ts`): one self-contained `.html`, real text in a `<pre>` with `<span>` runs per color, the font embedded as base64 (the whole ~22 kB woff2 — no subsetting tool in the build — Departure Mono, plus JetBrains Mono when "Smooth" is the project's font), background color, Play/Pause button, the project's FPS, holds and playback mode (loop/ping-pong/once); frame 1 is in the markup so it reads even without scripts, and the text is selectable. Sizing uses the font's measured advance so the art keeps the project's proportions in any window.
- **Sprite sheet**: one PNG grid (automatic near-square columns or a set number); with the JSON option the PNG and the JSON (each frame's rectangle and duration in ms) are delivered together as one `.zip`, since a share sheet/download of two files at once is unreliable on iPad.
- **PNG sequence** zip names files `<name>_0001.png…`; "Repeat held frames as duplicate files" writes a hold as repeated numbered files, otherwise one file per frame.
- **File names** follow §15.1 (`<project>_<ascii|raster>[_f0004].<ext>`; the frame suffix is used when a single frame is exported).
- **Project file (`.buddy`)** (`engine/projectFile.ts`, `state/projectFileActions.ts`): a ZIP with `project.json` (`format`, `schemaVersion`, the project, plus a list of cel metadata/overrides, reference cels and images), `cels/<track>/<frame>.bin` (16-byte bounding-box header + the raw indexed pixels), `images/<id>.<ext>` and `thumbnail.png` (frame 1 in the project's current view). Import validates the archive and every cel (sizes, bounds, missing images), migrates by `schemaVersion` (only version 1 exists; a *newer* file is refused with a clear message), and always creates a **new project with new ids** (a duplicate name becomes "… copy") — importing twice makes two copies. Images and cels are written before the project record, and a failed import is rolled back. **Round trip verified in the browser:** the imported project's JSON (minus id/name/timestamps) is identical, every cel's bytes/bbox/version/override are identical, and reference images and transforms come back (with fresh image ids). Export sets `lastExportedAt` *without* touching `updatedAt`, so a backup doesn't reorder the Projects screen. The Projects screen has Import project file and, in each project's menu, Export project file… and "Last backup: 3 days ago".
- **Storage-full alert** (§14.1): if a save fails, the editor now says so (a specific "Storage is full" message for quota errors) and offers Export project file right there. (Before this, save errors were only shown on the Projects screen.)
- **Not done / for later:** keyboard shortcut ⌘E is shown in the menu but not bound (Phase 9 owns shortcuts); ANSI and SVG are Phase 9 nice-to-haves.

## Phase 9 — Polish

- **The icon set was redrawn by hand** (`src/ui/iconBitmaps.ts`, 29 icons, each a 16×16 grid of `#`/`.` strings). The earlier icons were generated from geometric rules (rings, diagonals, ellipses) and it showed: off-centre, fuzzy, unreadable at size (the onion looked like a globe, "i" was lopsided). Now: every icon is a plain bitmap you can read and edit; **the settings icon is the supplied hammer-and-sickle drawing, pixel for pixel** (its 18×18 sampling grid was recovered from the image and the 14×14 art centred in the tile; a test pins it against the supplied art); icons are drawn at whole multiples of 16 px only (16 inline, 32 on buttons) so a pixel is never smeared across screen pixels (the old code drew them at 14, 18, 20, 22 and 28 px). A test checks every bitmap is a clean 16×16 grid and centred within a pixel. `tools/icon-sheet.mjs` renders all icons into one contact sheet (each enlarged, at 1× and 2×, inverted, with centre guides) for review, and `tools/build-icons.py` regenerates the symmetric ones.
- **Text characters that stood in for icons were replaced too:** the transport buttons (`|◀ ◀ ▶ ▶ ▶|`, `■`, `+▭`), the timeline chevrons (`▲▼`), undo/redo (`↶ ↷`), focus mode (`Fx`), the app menu (`▣`, now a pixel heart for "ascii_buddy<3") and the project card's `…` (now three pixel dots). New icons: layers (a stack, so it's no longer the same picture as "photo"), focus, more, heart, and the media set. The empty-reference-track button is now *plus + dashed frame* instead of a second plain photo.
- **Focus mode** (`F`, the View menu, or the toolbar button): the menu bar, tool palette, timeline and floating windows are hidden and a small exit button sits in the top-right corner (Esc or `F` also exit). The canvas isn't remounted, so pencil, gestures, undo and playback keep working. It is never persisted and resets when a project closes. **While a dialog is open the letter shortcuts are ignored** (before, typing in the export dialog's number field was safe but pressing `B` with a dialog open switched tools underneath it).
- **New shortcut:** ⌘E opens Export (the menu already showed it). The rest of Appendix A already existed from earlier phases.
- **Left-handed layout** was already wired (the palette moves right); its divider line now moves to the palette's inner side too.
- **App settings:** autosave delay is now adjustable (0.5–5 s); persistent storage shows "Granted / Request / Not supported" plus a plain explanation; and `navigator.storage.persist()` is requested when the *first project is created* (§14.1). **"Canvas rotation gesture" is shown as "Not available yet"**: the setting existed but nothing implemented rotation, and a toggle that does nothing is worse than an honest label. Rotating the view touches every coordinate mapping (drawing, selection, references, overlays) — it's in IDEAS.md rather than rushed in at the end.
- **ANSI and SVG export** (§15.2 nice-to-haves): ANSI is 24-bit colored text (one escape per color run, reset at each line end; optional project background; several frames each clear the screen first so `cat file.ans` plays as a flip-book). SVG is one frame of real, editable `<text>` runs, each pinned to its grid cells with `textLength` so the art doesn't depend on which font a viewer falls back to, with the font embedded and an optional transparent background. Both are unit-tested; the SVG was rendered in a browser and matched the app.
- **Optional offline mode** (`public/sw.js`, registered only when hosted over http(s) in a production build): keeps a copy of `index.html` (stale-while-revalidate, so an update appears the next time the app opens). Verified: it installs, caches the page, and the app then loads with the server stopped. The app doesn't depend on it.
- **Performance pass against §18 — desktop numbers only, no iPad here** (a busy 2048×1536 frame, 60 strokes): grid statistics 5–11 ms at 80–320 columns; Ramp conversion < 1 ms; Shape conversion 5.7 ms (80 cols), 15 ms (160), 41 ms (320) — a full-frame recompute at 320 columns in Shape is far inside the 500 ms budget even at several times slower hardware, and it already runs in a worker. Launch of the built single file to first paint: ~0.5 s (desktop; 230 kB transferred, gzip). Playback prep for a 189-frame reference-heavy project was ~1.1 s (Phase 7 follow-up). What I can't measure is Pencil latency at 120 Hz and the 100-frame/4 GB memory case on a real iPad, which is why those stay on the checklist.
